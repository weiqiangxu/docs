## 一、分布式事务概念

### 什么是分布式事务？

**分布式事务**是指事务的参与者、支持事务的服务器、资源服务器以及事务管理器分别位于不同的分布式系统的不同节点之上。

```mermaid

    B --> C[服务A<br/>数据库A]
    B --> D[服务B<br/>数据库B]
    B --> E[服务C<br/>数据库C]
    
    C --> F[本地事务]
    D --> G[本地事务]
    E --> H[本地事务]
    
    style B fill:#e1f5fe
    style C fill:#c8e6c9
    style D fill:#c8e6c9
    style E fill:#c8e6c9
```

### 为什么需要分布式事务？

**单体应用时代：**
- 单一数据库，使用本地事务（ACID）
- 通过数据库的事务机制保证数据一致性

**微服务时代：**
- 业务拆分为多个服务
- 每个服务有自己的数据库
- 跨服务的业务操作需要保证数据一致性
- 本地事务无法解决跨数据库的一致性问题

## 二、理论基础

### CAP 定理

> **一致性（Consistency）、可用性（Availability）、分区容忍性（Partition Tolerance）三个特性最多只能同时满足其中两个**

```mermaid
graph TD
    A[CAP定理] --> B[CA: 一致性+可用性]
    A --> C[CP: 一致性+分区容忍]
    A --> D[AP: 可用性+分区容忍]
    
    B --> B1[传统单机数据库<br/>RDBMS]
    C --> C1[分布式数据库<br/>MongoDB/HBase]
    D --> D1[分布式缓存<br/>Cassandra/DynamoDB]
    
    style A fill:#e1f5fe
    style B fill:#c8e6c9
    style C fill:#fff3e0
    style D fill:#ffcdd2
```

**详细说明：**

| 组合 | 说明 | 典型系统 | 应用场景 |
|------|------|---------|---------|
| **CA** | 放弃分区容忍性，单机系统 | MySQL、PostgreSQL | 传统单机应用 |
| **CP** | 放弃可用性，保证一致性 | HBase、MongoDB | 金融系统、配置中心 |
| **AP** | 放弃一致性，保证可用性 | Cassandra、DynamoDB | 社交网络、推荐系统 |

**CAP 权衡：**

1. **多节点为了数据一致性，数据同步阻塞服务，可用性就会变差**
2. **多节点为了高可用，但数据同步不及时，一致性变差**
3. **多节点因为部分节点连接中断，而无法正确提供服务，此为容忍性**

### BASE 理论

> **Basically Available（基本可用）、Soft State（软状态）、Eventually Consistent（最终一致性）**

```mermaid
graph LR
    A[BASE理论] --> B[基本可用]
    A --> C[软状态]
    A --> D[最终一致性]
    
    B --> B1[系统出现故障时<br/>允许损失部分可用性]
    C --> C1[允许系统存在<br/>中间状态]
    D --> D1[经过一段时间后<br/>最终达到一致]
    
    style A fill:#e1f5fe
    style B fill:#c8e6c9
    style C fill:#fff3e0
    style D fill:#c8e6c9
```

**BASE vs ACID：**

| 特性 | ACID | BASE |
|------|------|------|
| **一致性** | 强一致性 | 最终一致性 |
| **可用性** | 较低 | 较高 |
| **性能** | 较低 | 较高 |
| **复杂度** | 简单 | 复杂 |
| **适用场景** | 传统数据库 | 分布式系统 |

### 1. 两阶段提交（2PC）

**核心思想：** 通过协调者统一调度所有参与者的行为

```mermaid
sequenceDiagram
    participant C as 协调者
    participant P1 as 参与者1
    participant P2 as 参与者2
    
    Note over C: 阶段一: Prepare
    C->>P1: Prepare请求
    C->>P2: Prepare请求
    
    P1->>P1: 执行事务<br/>不提交
    P2->>P2: 执行事务<br/>不提交
    
    P1->>C: Yes/No
    P2->>C: Yes/No
    
    Note over C: 阶段二: Commit/Rollback
    alt 所有参与者都Yes
        C->>P1: Commit请求
        C->>P2: Commit请求
        P1->>P1: 提交事务
        P2->>P2: 提交事务
    else 有参与者No
        C->>P1: Rollback请求
        C->>P2: Rollback请求
        P1->>P1: 回滚事务
        P2->>P2: 回滚事务
    end
```

**优点：**
- 强一致性保证
- 实现相对简单
- 业界成熟方案

**缺点：**
- 同步阻塞问题
- 单点故障问题
- 数据不一致风险（协调者故障时）

**适用场景：**
- 对一致性要求极高的场景
- 数据库层面的分布式事务

### 2. 三阶段提交（3PC）

**核心思想：** 在2PC基础上增加CanCommit阶段，引入超时机制

```mermaid
sequenceDiagram
    participant C as 协调者
    participant P1 as 参与者1
    participant P2 as 参与者2
    
    Note over C: 阶段一: CanCommit
    C->>P1: CanCommit请求
    C->>P2: CanCommit请求
    
    P1->>C: Yes/No
    P2->>C: Yes/No
    
    Note over C: 阶段二: PreCommit
    alt 所有参与者都Yes
        C->>P1: PreCommit请求
        C->>P2: PreCommit请求
        
        P1->>P1: 执行事务<br/>不提交
        P2->>P2: 执行事务<br/>不提交
        
        P1->>C: Ack
        P2->>C: Ack
        
        Note over C: 阶段三: DoCommit
        C->>P1: DoCommit请求
        C->>P2: DoCommit请求
        
        P1->>P1: 提交事务
        P2->>P2: 提交事务
    else 有参与者No
        C->>P1: Abort请求
        C->>P2: Abort请求
    end
```

**优点：**
- 减少阻塞时间
- 引入超时机制
- 参与者可自主决策

**缺点：**
- 可能出现数据不一致
- 实现复杂
- 网络开销大

**适用场景：**
- 对可用性要求较高的场景
- 需要减少阻塞时间的场景

### 3. 可靠事件队列

**核心思想：** 通过消息队列实现最终一致性

```mermaid
graph LR
    A[服务A] --> B[消息队列]
    B --> C[服务B]
    
    A --> A1[执行本地事务]
    A1 --> A2[发送消息到MQ]
    
    B --> B1[持久化消息]
    B1 --> B2[投递给消费者]
    
    C --> C1[接收消息]
    C1 --> C2[执行本地事务]
    C2 --> C3[发送ACK]
    
    style A fill:#e1f5fe
    style B fill:#fff3e0
    style C fill:#c8e6c9
```

**实现方式：**

```mermaid
sequenceDiagram
    participant A as 服务A
    participant MQ as 消息队列
    participant B as 服务B
    
    A->>A: 执行本地事务
    A->>MQ: 发送消息
    
    alt 发送成功
        MQ->>MQ: 持久化消息
        MQ->>B: 投递消息
        B->>B: 执行本地事务
        B->>MQ: ACK确认
    else 发送失败
        A->>A: 重试发送
    end
```

**优点：**
- 实现简单
- 解耦服务
- 异步执行，性能好
- 最终一致性保证

**缺点：**
- 只有最终一致性
- 消息重复消费问题
- 需要处理幂等性

**适用场景：**
- 对实时性要求不高的场景
- 允许最终一致性的业务
- 高并发场景

**最大努力交付（Best-Effort Delivery）：**

```
可靠事件队列只要第一步业务完成了，后续就没有失败回滚的概念，只许成功，不许失败
靠着持续重试来保证可靠性的解决方案
```

### 4. TCC 事务（Try-Confirm-Cancel）

**核心思想：** 将业务逻辑拆分为三个阶段


# TCC vs Saga（Seata‑Go，Go+GORM+MySQL）
> 最核心区别：
- **TCC：Try‑预留资源 → Confirm真实生效 / Cancel释放资源；追求隔离，**强一致性**，不会暴露脏中间状态。
- **Saga：直接执行正向本地事务（立刻提交），失败反向跑补偿；**最终一致性**，会暴露中间脏状态，没有资源预留阶段。

> 注意：Saga**不是强一致**，资金、转账核心账务业务**严禁直接用Saga**。

## 原理通俗对比
### TCC
`Try(检查+冻结资源) → [全部Try成功] → Confirm(真正执行业务)`
任意Try失败 → `Cancel(解冻释放资源)`
> Try阶段只是冻结，真实业务结果要等到Confirm才落地；外部看不到“已经扣钱”的中间态。

### Saga
`T1(本地事务直接提交) → T2(本地事务直接提交) → T3`
如果T3失败，**反向执行补偿 C2、C1**
> T1执行完数据库立刻提交，其他请求立刻可以读到T1的数据；此时如果后续失败，再去做补偿撤销。

## Go伪代码对比（同一个转账场景）
### TCC（前面给过，精简）
```go
// TCC三接口
type TCCResource interface {
    Try(ctx context.Context, arg interface{}) (bool, error)
    Confirm(ctx context.Context, arg interface{}) (bool, error)
    Cancel(ctx context.Context, arg interface{}) (bool, error)
}

// Try：冻结余额，不真正扣钱；GORM本地事务
func (s *AccountTCC) Try(ctx context.Context, arg interface{}) (bool, error) {
    tx := s.db.WithContext(ctx).Begin()
    // 校验余额，冻结 frozen_balance
    // 写入tcc_record状态记录
    return true, tx.Commit().Error
}
// Confirm：真正扣掉冻结余额
func (s *AccountTCC) Confirm(ctx context.Context, arg interface{}) (bool, error) {
    tx := s.db.WithContext(ctx).Begin()
    // 扣减 frozen_balance
    return true, tx.Commit().Error
}
// Cancel：解冻，把钱退回可用余额
func (s *AccountTCC) Cancel(ctx context.Context, arg interface{}) (bool, error) {
    tx := s.db.WithContext(ctx).Begin()
    // 恢复余额、解冻
    return true, tx.Commit().Error
}
```

### Saga伪代码（Go）
> Saga没有Try阶段；每个正向操作直接`Begin‑Commit`；配套一个**补偿函数**；Seata‑Go状态机调度，失败逆向跑补偿。

```go
// Saga：正向操作 + 补偿操作，每个都是独立gorm本地事务
// 正向：转出扣款（直接提交）
func TransOut(ctx context.Context, param *TransferParam) error {
    tx := db1.WithContext(ctx).Begin()
    // 直接扣可用余额，没有冻结，事务直接提交
    err := tx.Model(&Account{}).
        Where("user_id=?", param.FromUserId).
        UpdateColumn("balance", gorm.Expr("balance - ?", param.Amount)).Error
    if err != nil {
        _ = tx.Rollback().Error
        return err
    }
    return tx.Commit().Error
}

// 补偿：转出退款（对应TransOut的回滚逻辑）
func CompensateTransOut(ctx context.Context, param *TransferParam) error {
    tx := db1.WithContext(ctx).Begin()
    // 把钱加回去；必须做幂等！
    err := tx.Model(&Account{}).
        Where("user_id=?", param.FromUserId).
        UpdateColumn("balance", gorm.Expr("balance + ?", param.Amount)).Error
    if err != nil {
        _ = tx.Rollback().Error
        return err
    }
    return tx.Commit().Error
}

// 正向：转入加钱
func TransIn(ctx context.Context, param *TransferParam) error {
    tx := db2.WithContext(ctx).Begin()
    err := tx.Model(&Account{}).
        Where("user_id=?", param.ToUserId).
        UpdateColumn("balance", gorm.Expr("balance + ?", param.Amount)).Error
    if err != nil {
        _ = tx.Rollback().Error
        return err
    }
    return tx.Commit().Error
}

// 补偿：转入扣回
func CompensateTransIn(ctx context.Context, param *TransferParam) error {
    tx := db2.WithContext(ctx).Begin()
    err := tx.Model(&Account{}).
        Where("user_id=?", param.ToUserId).
        UpdateColumn("balance", gorm.Expr("balance - ?", param.Amount)).Error
    if err != nil {
        _ = tx.Rollback().Error
        return err
    }
    return tx.Commit().Error
}

// seata‑go saga状态机定义：顺序执行 TransOut → TransIn；失败反向 CompensateTransIn → CompensateTransOut
// tm.WithSagaTx(ctx, stateMachineDef, params)
```

> 风险：TransOut成功提交，TransIn失败；**这一段时间A账户钱已经被扣掉，业务上看到A少钱，B没加钱；之后补偿才把钱退回去**，存在短暂不一致窗口。

## TCC vs Saga完整对比表
|维度|TCC（Try‑Confirm‑Cancel）|Saga（正向+补偿）|
|---|---|---|
|**一致性**|业务层强一致；无脏中间状态；资源先预留再生效|**最终一致性；存在脏中间状态，外部可读到不完整数据**|
|阶段划分|3阶段：Try / Confirm / Cancel|2组：正向操作、补偿操作；无预留阶段|
|数据提交时机|Try只冻结，Confirm才真正落地；Try的修改是冻结状态|**每一步正向执行完立刻commit本地事务**，数据对外可见|
|表改造|需要冻结字段 `frozen_xxx`；`tcc_record`事务表|不需要冻结字段；需要saga状态表；补偿逻辑要幂等|
|隔离性|好，冻结资源，防止超卖、脏读|差，无隔离；并发场景容易超卖、数据错乱|
|代码侵入|高：每个分支写Try/Confirm/Cancel三套逻辑|中：每个分支写正向+补偿两套逻辑|
|长事务支持|适合短事务；Try资源会被业务冻结，不能跑几小时|**非常适合长流程（分钟/小时级）**，不持有数据库锁|
|故障回滚|Cancel释放Try预留资源|反向执行补偿，撤销已经提交的业务数据|
|经典坑|幂等、空回滚、悬挂|补偿幂等、脏读、补偿风暴、并发超卖|
|支持异构存储|✅支持MySQL/Redis/第三方HTTP|✅支持MySQL/Redis/第三方HTTP|
|适合场景|支付、转账、账务、库存扣减，**不能接受中间脏数据**|订单履约、物流、长业务流程，可以容忍短暂不一致|

## 故障场景对比
### TCC
1. Try全部成功，TC宕机：资源处于冻结状态；定时任务扫描`tcc_record`TRY状态做兜底Cancel。
2. 网络乱序：Cancel先到，Try后到 → **悬挂问题，业务代码必须拦截**。
3. Confirm/Cancel被重试：依靠tcc_record状态做幂等。

### Saga
1. T1成功提交，T2执行失败：T1的数据已经对外可见，此时业务处于不一致；框架执行C1补偿恢复。
2. 补偿阶段服务宕机：需要**不断重试补偿**；补偿必须保证幂等，不能二次退款/扣库存。
3. 并发风险：Saga没有资源预留，并发下单会出现超卖，需要业务层乐观锁/版本号控制。

## 选型决策（Go+GORM+Seata‑Go）
1. **必须强一致，不能出现脏中间状态（资金账务）**
    - 只用MySQL：优先选 **Seata‑XA**（开发成本最低）
    - 需要对接Redis/第三方接口：选 **TCC**，接受高开发成本，处理空回滚、悬挂、幂等。

2. **长业务流程，可以容忍短暂数据不一致（订单履约、物流）**
    → 选 **Saga**。

3. ❌绝对不要：资金交易用Saga；Saga“先扣钱再退款”，中间窗口会资损风险。

4. 混合模式：核心资金链路TCC/XA；外围通知、物流、非核心步骤用Saga。

## 补充：四种模式快速总览
- **Seata‑XA：数据库层2PC，强一致，MySQL Only，低业务侵入，锁时间长**
- **Seata‑TCC：业务层2PC，强一致，异构存储，开发成本高**
- **Seata‑AT：快照回滚，最终一致，MySQL Only，低侵入**
- **Seata‑Saga：补偿模式，最终一致，长流程，异构存储，允许脏中间状态**

**优点：**
- 性能较好（资源锁定时间短）
- 最终一致性保证
- 灵活性高

**缺点：**
- 业务侵入性强
- 开发成本高
- 需要实现三个接口
- 需要处理幂等性

**适用场景：**
- 对性能要求较高的场景
- 业务逻辑复杂的场景
- 需要精细化控制资源的场景

**关键点：**
- 用户花钱了冻结金额，用户买书了就冻结书籍状态，讲究资源锁定
- 业务侵入性很强

### 5. SAGA 事务

```mermaid
    O->>P: T2: 扣款
    P->>P: 执行扣款
    P->>O: 扣款成功
    
    O->>I: T3: 扣减库存
    I->>I: 执行扣减
    I->>O: 库存不足!
    
    Note over O: 反向补偿流程
    O->>P: C2: 退款
    P->>P: 执行退款
    P->>O: 退款成功
    
    O->>O: C1: 取消订单
    O->>O: 订单已取消
```

**设计约束：**

1. **子事务必须原子行为**
2. **Ti和Ci都具备幂等性**
3. **Ti与Ci满足交换律**
4. **Ci必须能成功提交**

**优点：**
- 适合长事务
- 最终一致性保证
- 性能较好

**缺点：**
- 没有隔离性
- 补偿逻辑复杂
- 可能出现脏读

**适用场景：**
- 长事务场景
- 跨多个服务的业务流程
- 对性能要求较高的场景

**两种恢复模式：**

1. **正向恢复（Forward Recovery）**
   - Ti事务提交失败，则一直对Ti进行重试，直至成功为止
   - 执行模式为：T1，T2，…，Ti（失败），Ti（重试）…，Ti+1，…，Tn

2. **反向恢复（Backward Recovery）**
   - Ti事务提交失败，则一直执行Ci对Ti进行补偿，直至成功为止
   - 执行模式：T1，T2，…，Ti（失败），Ci（补偿），…，C2，C1

## 六、最佳实践

### 1. 幂等性设计

所有分布式事务方案都需要考虑幂等性：

```java
public class IdempotentService {
    
    private Map<String, Boolean> processedRequests = new ConcurrentHashMap<>();
    
    public boolean process(String requestId, Runnable action) {
        // 检查是否已处理
        if (processedRequests.containsKey(requestId)) {
            return true;
        }
        
        // 执行业务逻辑
        action.run();
        
        // 标记为已处理
        processedRequests.put(requestId, true);
        return true;
    }
}
```

## 七、总结

### 核心要点

1. **分布式事务是微服务架构的必然挑战**
2. **没有完美的解决方案，需要根据业务场景选择**
3. **强一致性方案性能低，最终一致性方案性能高**
4. **幂等性、超时、监控是所有方案的共同要求**
